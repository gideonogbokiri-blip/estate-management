# Estate backend foundation (greenfield)

This workspace is a standalone estate-management product. Its API, identity, persistence, access control and audit records are implemented and owned here. Product briefs provide domain requirements; any language in older notes that assumes another application's identity or services is superseded by this greenfield architecture.

The chosen greenfield stack and first vertical-slice order are recorded in [ARCHITECTURE.md](ARCHITECTURE.md).

Current connected feature groups include estate applications and platform review, membership and access, properties and structure, ownership and tenancy, visitor/gate security, resident join requests, maintenance, incidents, facilities, announcements, billing records, budgets, expense decisions and manual settlement reconciliation. Flutter onboarding, manager and resident screens use the standalone API for their connected workflows. External payment processing and notification delivery integrations remain separate work.

## Local API foundation

The API is an independent NestJS application with its own PostgreSQL schema. For a local run, copy `.env.example` to `.env`, set a unique database password and a randomly generated `ACCESS_TOKEN_SECRET` of at least 32 bytes, install dependencies with `npm ci`, create/start PostgreSQL, generate the Prisma client, apply the development migration, then start the API with `npm run start:dev`. Readiness is exposed at `GET /api/v1/health/ready`; liveness is `GET /api/v1/health/live`.

### First platform administrator

Platform role grants are not exposed through public registration or an HTTP role-management route. After an operator has verified that the selected email belongs to the intended active account, build the API and run the explicit bootstrap command from this directory:

```powershell
npm run build
npm run bootstrap:platform-super-admin -- admin@example.com GRANT_PLATFORM_SUPER_ADMIN:admin@example.com
```

The command requires the exact normalized email twice, grants only `platform_super_admin`, and writes an operator-CLI audit event in the same database transaction. Repeating it for an account that already has the grant makes no change. The first platform administrator can then sign in at the platform review app and review or approve estate applications. Keep use of this command on an operator-controlled machine with database access.

### Local presentation demo

For a presentation on this computer, build the API and run `npm run seed:demo -- --confirm-local-demo`. The command refuses non-loopback database hosts, production mode and databases that already contain accounts or estates. It creates one estate administrator, one resident, six properties, an active resident occupancy, one charge definition, a published announcement and a community facility. It prints randomly generated login passwords once; save them before closing the terminal. The seeded bank account and invoice ledger remain empty, so the demo does not display fake payment instructions or claim a payment. These are illustrative local records, not production customer data.

Available routes:

- `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`.
- `POST /api/v1/estate/applications`, `GET /api/v1/estate/applications/mine`, `PATCH /api/v1/estate/applications/:applicationId`, and `POST /api/v1/estate/applications/:applicationId/submit` (bearer access token required).
- `GET /api/v1/estate/estates/mine` returns only the authenticated user's active estate memberships.
- `GET` and `PATCH /api/v1/estate/estates/:estateId/settings` read and update an estate's name, type and location. Reads require an active administrator or manager membership; updates require an active estate-administrator membership and write an audit event in the same transaction.
- `GET /api/v1/estate/estates/available` and `GET /api/v1/estate/estates/:estateId/join-properties` provide safe active-estate/property choices for a signed-in applicant.
- `GET /api/v1/estate/estates/:estateId/properties`, `POST` on the same collection, and `PATCH /api/v1/estate/estates/:estateId/properties/:propertyId` (active estate administrator/manager membership required).
- `GET /api/v1/estate/estates/:estateId/structure`, `POST .../structure/nodes`, `PATCH .../structure/nodes/:nodeId`, and `DELETE .../structure/nodes/:nodeId` (active estate administrator/manager membership required; archive requires no active children or linked properties).
- `POST /api/v1/estate/residents/join-requests`, `GET .../residents/join-requests/mine`, and `GET .../residents/join-requests/:requestId` for the signed-in applicant.
- `GET /api/v1/estate/estates/:estateId/resident-requests`, with `POST .../:requestId/approve` and `POST .../:requestId/reject` (active estate administrator/manager membership required; decisions are single-winner, audited transactions).
- `GET /api/v1/estate/estates/:estateId/ownership`, `GET/POST .../properties/:propertyId/owners`, and `POST .../ownership/:ownershipId/verify|end` manage estate ownership history. Writes are audited; overlapping shares are capped at 100%, and verification decisions require an estate manager and a reason.
- `GET /api/v1/estate/landlord/estates/mine` returns estates where the signed-in account has effective verified ownership; `GET /api/v1/estate/estates/:estateId/landlord/portfolio` returns its verified properties and current occupancy.
- `GET /api/v1/estate/estates/:estateId/tenancies`, `POST .../properties/:propertyId/tenancies`, `POST .../tenancies/:tenancyId/approve`, and `POST .../tenancies/:tenancyId/terminate` provide manager tenancy lifecycle basics. Rent payees must have verified ownership covering the term; approval activates tenant membership and occupancy in one transaction. Rent records are terms only, not invoices or payment balances.
- `GET /api/v1/estate/tenancies/mine` returns only the signed-in tenant's currently effective approved terms, safe property and estate context, and landlord display name.
- `POST /api/v1/estate/maintenance/requests` requires an `Idempotency-Key` and an active occupancy, tenancy or verified ownership link to the selected property. `GET /api/v1/estate/maintenance/requests/mine?estateId=...` returns the caller's own requests and resident-visible updates. Private attachments are not accepted until the private-file service exists.
- `GET /api/v1/estate/estates/:estateId/maintenance/requests` and `POST .../:requestId/review` are limited to active estate administrators/managers. The queue accepts bounded `page`/`pageSize`, status (including `open`) and text search across safe request fields; filtering is applied within the authorized estate before counts and pagination. The review endpoint applies the maintenance state machine, records status history and audit events, and keeps internal notes out of resident responses. Notification records are queued in the maintenance outbox; a delivery worker is not connected yet.
- `POST /api/v1/estate/estates/:estateId/security-incidents`, `GET .../security-incidents/mine`, `GET .../security-incidents`, and `POST .../:incidentId/review` provide authenticated incident reporting and staff review. `POST .../:incidentId/evidence` accepts idempotent PDF/JPEG/PNG uploads up to 10 MB after signature validation; `GET .../:incidentId/evidence/:evidenceId/content` returns a private file only to the reporter or an authorized incident reviewer. Upload and content access are audited. Evidence files are stored outside the public web root. Incident notifications are not delivered yet.
- `GET /api/v1/platform/applications`, `GET /api/v1/platform/applications/:applicationId`, and review transitions at `/start-review`, `/assign`, `/request-information`, `/reject`, and `/approve` (platform grant required; approval requires `platform_super_admin`).
- `GET /api/v1/estate/estates/:estateId/announcements` and `POST` on that collection create/list manager drafts; `POST .../:announcementId/publish` publishes into the estate feed. `GET /api/v1/estate/announcements/mine` and `POST .../:announcementId/read` are scoped to active resident/landlord memberships.
- `GET /api/v1/health/live` and `GET /api/v1/health/ready`.

The Prisma schema covers accounts and sessions; estate applications, private documents, platform review, estates and memberships; properties, structure, ownership, occupancy and tenancies; visitor passes, gate visits and security evidence; charges, invoice records and manual settlements; budgets and expense approvals/settlements; maintenance, incidents, facilities, announcements, notifications and audit history. The app currently supports application and incident document upload, but not tenancy-agreement storage or maintenance attachments. Expense and invoice settlements are staff-entered records after an offline check; there is no payment initiation, bank feed or provider webhook integration. Password recovery, automated tenancy expiry/renewal and outbound email/SMS/push delivery remain to be implemented. First platform administrator provisioning is available through the operator-controlled bootstrap command above.

## Module boundaries

```text
backend/
  modules/
    onboarding/       application lifecycle and approval decision rules
    estates/          approved estate aggregate and operational-state guard
    access/           estate membership, permission checks and estate context
    properties/       estate structure, properties, ownership and property history
    people/            ownership, resident membership and tenancy history
    visitors/          invitations, verification and append-only access events
    billing/           charges, rent schedules, invoices and adjustments
    payments/          provider-neutral payment orchestration and verification
    operations/         maintenance, incidents, facilities and announcements
    finance/            budgets, expenses and reconciliation
    subscriptions/      versioned plans and estate subscription agreements
    reporting/          estate-scoped read models
  shared/
    audit/              append-only audit event service
    files/              private file storage and short-lived access grants
    notifications/      notification outbox and delivery adapters
```

Keep domain rules separate from HTTP request/response mapping and infrastructure adapters. The dependency direction is domain rules <- use cases <- this product's repositories and services <- HTTP controllers. Implement shared identity, authorization, payments, notifications, private files and audit as owned modules with clear boundaries; feature modules must use those shared services.

`modules/billing/list-my-landlord-rent-invoices.js` composes the landlord Rent view from the existing actor-scoped estate invoice list. It supplies only the server-configured rent category and bounded pagination, so callers cannot choose payer/property/tenancy IDs. The connected invoice access resolver and query adapter still own verified landlord/payee authorization, estate and relationship scoping, and balances derived from verified payment allocations. This is a framework-independent use-case seam; it is not an HTTP route or persistence adapter.

`modules/billing/list-my-landlord-property-charge-invoices.js` similarly composes the landlord Charges view from a server-configured category allowlist. The generic invoice query accepts either one category or a bounded category list so the repository can scope categories before pagination. The same authenticated landlord relationship resolver and verified-allocation balance derivation remain mandatory.

`modules/properties/list-estate-map-assets.js` provides a bounded map read seam. Its access adapter must authorize the estate and its query adapter must authorize each asset/layer before returning coordinates. The use case validates coordinate pairs and explicit confidence state, restricts labels to safe projections, and never receives device location. GIS provider and persistence adapters remain host-owned.

`modules/properties/update-estate-map-asset-location.js` composes the map-location write command. Its resolver must enforce both `map.location.manage` and the target asset's management permission, return only estate-configured location sources, and bind actor, estate, type and asset IDs. The command locks and revalidates the same-estate asset, checks WGS 84 bounds, coordinate-pair completeness, accuracy and confidence consistency, then commits the new location and an audit record containing the reason plus previous/new safe location values in one transaction. The adapter must serialize this command with asset archive/reparent operations and must never accept a person/device location.

`modules/people/list-my-landlord-property-documents.js` lists safe document metadata after scoping records to active verified landlord properties. `modules/people/access-landlord-property-document.js` rechecks that relationship and document policy on every open, obtains a short-lived HTTPS grant from the existing private-file service, and audits access. See `Zvend_Estate_Property_Documents_Contract.md`; neither module is a deployed HTTP route or storage adapter.

`modules/operations/list-my-landlord-property-maintenance.js` adds a landlord-specific read seam scoped to active verified owned properties and explicit maintenance-view permission. Its projection excludes requester contact, private notes and attachment references. See `Zvend_Estate_Landlord_Maintenance_Contract.md`; route and host repository adapters remain to be connected.

## Current implementation

`modules/onboarding/application-decision.js` contains pure decision-planning rules for the first approval workflow. It validates state transitions and required decision inputs, and returns the state changes and audit events a persistence adapter must commit. Approval explicitly activates the estate and assigns the initial `estate_administrator` role in one effect set. The approval use case records separate application-decision and estate-membership assignment audit events after the adapter returns the created IDs. The function does not perform authorization, database writes, document access, notifications, or HTTP handling.

`modules/onboarding/create-estate-application-draft.js` creates a blank draft for the authenticated applicant through an injected repository and appends its audit event in the same transaction. It never accepts the applicant ID from the request body.

`modules/onboarding/application-lifecycle.js` plans applicant draft edits, submission/resubmission and reviewer transition into the review state. Draft edits use contract-level canonical fields and cannot change applicant, reviewer or status fields. Submission requires server-provided field and document-category policy, and only uses document categories already verified by the trusted file adapter. Review start rejects a conflicting assigned reviewer. Each planner returns state effects and audit events for atomic persistence; permission checks, application locking, file ownership checks and writes remain use-case/repository responsibilities.

`modules/onboarding/estate-lifecycle.js` defines the operational estate statuses, the proposed application-to-estate mapping and explicit suspend, reactivate and deactivate transitions. Each transition requires a reason and produces a safe audit record; arbitrary status patches are not supported. `modules/onboarding/transition-estate-lifecycle.js` requires platform permission, a locked estate lookup and a lifecycle policy adapter. That policy must confirm operational blockers before deactivation (for example, unresolved financial or occupancy obligations); state persistence and audit share one transaction, with estate access invalidation queued when access is disabled.

`modules/onboarding/submit-estate-application.js` composes the submission planner with an applicant-scoped, locked lookup, server submission policy, trusted verified-document lookup, one state commit and an audit append. Its transaction adapter must roll back both state and audit writes on failure. The file adapter must verify application ownership and document review state; this module does not read raw files or trust document IDs supplied by the client.

`modules/onboarding/start-estate-application-review.js` moves a submitted application into review through platform permission, an assigned-reviewer scoped locked lookup, and an atomic state/audit transaction. It uses the existing review-start planner; reviewer assignment and repository-level locking remain adapter responsibilities.

`modules/onboarding/list-estate-applications.js` returns a bounded platform review queue with status/search filters, deterministic newest-submission ordering, actor-authorized projections and reviewer-scope checks. Its repository must apply assigned-reviewer/platform scope before filtering, counting and pagination. Responses contain only the application summary and document counts; private document metadata/content must use a separate authorized detail operation.

`modules/onboarding/read-estate-application.js` provides the separate application detail read for an applicant or authorized reviewer. The repository lookup must scope the record to the actor before returning it; actor-aware projections may include allowed contact/application fields and safe document metadata only. It may return a non-sensitive document access identifier, but never a storage reference; retrieving file contents remains a separate short-lived private-file authorization operation.

`modules/onboarding/access-estate-application-document.js` rechecks actor/application/document scope, applies server-owned access policy and asks Zvend's existing private-file service for an HTTPS link capped at five minutes. It audits the document access and returns only the short-lived grant to the API adapter; the HTTP layer should redirect to that URL and must not log or persist the URL. Its lookup accepts a public document access identifier and resolves the private storage reference server-side.

`modules/onboarding/assign-estate-application-reviewer.js` supports first-time reviewer assignment for a submitted application. The use case requires the platform assignment permission, locks the submitted record, validates the target through the existing reviewer identity/permission adapter, then commits assignment and audit in one transaction. Reassignment is not included until the product policy defines who may transfer an active review.

`modules/onboarding/update-estate-application-draft.js` composes the partial-update planner with an applicant-scoped locked lookup and atomic state/audit writes. Request field names must be translated at the API boundary from the form names (such as `estateName`, `organization`, and `applicantRole`) to the canonical contract fields (`proposedName`, `managementEntityName`, and `applicantRelationship`).

`modules/onboarding/approve-estate-application.js` adds the first application/use-case seam around that planner. It requires platform approval permission, a reviewer-scoped and locked application lookup, eligibility of the selected existing Zvend user, and a transaction adapter. The adapter commits application, estate and initial membership effects, then appends the audit event in that same transaction. Its ports are intentionally injected; no HTTP framework, database schema, ORM, identity system or authorization implementation is assumed. This seam is not production-ready until wired to the actual Zvend services and checked against their conventions.

`modules/estates/estate.js` defines the approved operational estate record and guards normal operations to the selected active estate. Estates are created only from an approved application, with validated estate type, address, coordinates, code and optional explicitly selected timezone/currency. Application status and operational estate status remain separate concepts.

`modules/estates/commit-approved-estate.js` supplies a transactional repository composition for the estate and initial-admin portion of approval. The outer `commitDecisionEffects` adapter must commit the application decision in the same transaction, call this composition with the locked reviewed application and approving actor, and return the created estate/membership. The composition generates an estate ID and unique code through injected source-system ports, persists the Active estate and planned initial Active `estate_administrator` membership, and verifies both records so any failure rolls back the outer transaction. Adapt the ports and estate shape to Zvend's actual repositories and RBAC before binding it.

`modules/estates/read-estate-summary.js` implements the proposed estate-detail read behind `estate.view`, a trusted estate context and an estate-scoped repository lookup. Its response is an explicit allowlist of estate identity, active status, public location, optional timezone and currency; it never returns the raw persistence record or onboarding applicant contact data.

`modules/reporting/dashboard-summary.js` builds the proposed estate dashboard response from capability-filtered source aggregates. Property/occupancy, resident, tenancy, finance, visitor and maintenance sections are independently omitted unless the actor has a relevant estate/report capability. The source adapter receives only those requested sections and the estate-scoped reporting period; it must aggregate authoritative records under the same transaction/snapshot. Each returned section has explicit availability and source-freshness status. Financial inputs stay decimal strings at configured currency precision and net operating position is calculated exactly using minor units as collected rent/fees/charges less paid expenses. Period boundaries must be generated/interpreted in the estate timezone; no missing metric is filled with a sample value.

`modules/onboarding/decide-estate-application.js` orchestrates rejection and requests for more information. It requires review permission and an assigned-scope locked lookup, verifies the persisted next status, appends audit, and queues the applicant notification through an injected transactional outbox adapter. Approval remains a separate use case because it also activates the estate and assigns its first administrator.

`modules/access/estate-context.js` resolves an estate scope from active memberships loaded for the authenticated actor, checks estate capabilities, rejects malformed or platform-scoped grants, and hides cross-estate records as not found. `modules/access/resolve-estate-context.js` also verifies that repository results stay inside the requested actor/estate IDs (normalizing string/number representations). It does not authenticate the actor, load memberships, implement platform-level support access, or replace the source system's RBAC. Its permission values and record shapes must be mapped to Zvend's actual authorization model.

`modules/access/resolve-estate-context.js` adds an injected repository seam that loads active memberships for the authenticated actor and requested estate before invoking the domain resolver. The caller must obtain `actorUserId` from Zvend authentication, not request-body data. The repository must return trusted membership records and scope its query by both actor and estate. Platform support access remains a separate explicit authorization path and is not granted by this resolver.

`modules/access/list-accessible-estates.js` builds the estate-selector read model from active memberships returned for the authenticated actor. It rejects records outside the actor scope, filters inactive estates/memberships, deduplicates by normalized estate ID, and returns only estate ID, display name, optional code and location label. The repository adapter must derive the actor from authenticated context and query memberships with server-side scope.

`modules/access/get-estate-permissions.js` returns the actor's current, deduplicated estate capabilities for UI affordances. Its adapter must resolve the authenticated actor's effective grants from active membership/role and relationship policy in the requested estate. The response excludes platform permissions and is not an authorization token; each API operation must still recheck permission and record relationship server-side.

`modules/access/list-estate-team.js` returns a bounded estate-scoped page of memberships and invitations for `staff.view`. It requires the repository to scope before filtering/search/counts/pagination and applies an actor-aware allowlisted projection for contact, role and access-scope display. The response excludes credentials, invitation tokens, permission internals and audit metadata.

`modules/access/staff-membership.js` plans reason-required suspend/revoke transitions for another member while preserving the estate membership record and recording actor, reason, time and prior/next status. `modules/access/manage-estate-staff-membership.js` requires `staff.manage`, locks the target in the selected estate, applies lifecycle policy (including safeguards against removing required estate administrators), writes history and queues authorization-cache invalidation plus audit in the same transaction. Zvend's authorization service must check the current persisted membership state on each request; UI state and cache invalidation are not authorization controls.

`modules/access/staff-role-assignment.js` plans a reason-required role replacement for another active or suspended estate member. It rejects platform permissions and any role grant outside the assigning actor's delegated permission set, while retaining the before/after role and permission snapshot for history. `modules/access/assign-estate-staff-role.js` requires `staff.grant`, a locked estate-scoped membership, a trusted active estate role, a policy adapter for separation of duties and administrative continuity, atomic membership/history persistence, authorization invalidation and audit. Role data and delegable grants must come from the server authorization service; never accept permission arrays from the browser.

`modules/access/staff-invitation.js` plans an estate invitation only for an existing Zvend identity and a trusted role whose permissions are fully delegable by the actor; platform permissions are rejected and the selected role/grant snapshot is retained on the invite. `modules/access/invite-estate-staff.js` resolves `staff.invite` permission, account eligibility, estate role delegation, seat policy, duplicate membership/invitation state, then commits the invitation in the `invited` state, existing notification outbox message and audit event in one transaction. `modules/access/accept-estate-staff-invitation.js` locks the estate-scoped invitation, verifies the authenticated invitee, active estate, expiry and unchanged role snapshot, rechecks capacity, then activates membership and accepts the invitation with one audit event. These use cases do not create users or issue credentials themselves.

`modules/properties/property.js` validates property drafts and same-estate hierarchy links, rejects duplicate parent links and prevents new records from bypassing the archive workflow. It preserves unit/address/description and validates optional latitude/longitude pairs. It also plans a non-destructive archive only after the caller confirms there are no blocking relationships. The `active` property status means operational/available; occupancy is derived from effective occupancy records and remains a separate value. Estate-scoped code uniqueness, allowed hierarchy shapes, active relationship checks, authorization and persistence belong in the repository/service adapter and must use the rules confirmed in Zvend.

`modules/properties/create-property.js` adds an estate-scoped property creation use case. It resolves the actor's property-management permission, loads active hierarchy nodes from the selected estate, checks the estate's property-code rule, and commits the validated property and audit event together. Parent-node lookup and property creation must share locks with hierarchy reparent/archive workflows. The uniqueness lookup is advisory under concurrency; the real repository must also enforce the agreed estate/code uniqueness rule with a database constraint.

`modules/properties/update-property.js` defines an estate-scoped property edit command. It locks the property, allows only property code/type/status/unit/address/description/hierarchy changes, validates active same-estate parent nodes and changed property-code availability, then commits and audits atomically. Estate identity, ownership, occupancy, archive state and system fields cannot be patched through this operation. Production persistence must serialize it with property archive, hierarchy and relationship writers.

`modules/properties/list-estate-properties.js` provides the estate register read seam. It bounds pagination, validates status/type/hierarchy/occupancy/search filters, resolves property-view permission and queries within one transaction. The repository must scope before filtering/counting/pagination and derive occupancy at the supplied server timestamp. The actor-specific projector can add only safe display labels and occupied/vacant state; the use case builds the response from property identity/type/status fields and rejects unknown projection fields, duplicate rows, invalid values or cross-estate data. Keep owner/occupant labels out unless the actor's relationship policy grants that display.

`modules/properties/read-property-detail.js` supports staff permission or verified owner/tenant relationship access, then loads same-estate ownership and occupancy records and returns an allowlisted detail projection. Projected relationship IDs must come from the actor-authorized ownership/occupancy query results; duplicate or injected relationships fail closed. Projected property values must match or be redacted from the authorized source record. It returns property identity/description and permitted relationship display names, shares, dates and statuses only; document references, coordinates and raw relationship records are omitted. Evidence retrieval remains a separate private-storage authorization operation. A non-rented owner property is not assumed to be owner-occupied; occupancy remains a separate relationship.

`modules/people/list-estate-tenancies.js` provides the paginated `GET /api/estate/tenancies` read seam with estate-scoped tenancy permission, bounded date/status/search filters and an actor-specific projection. Its response allowlists property, tenant and optional landlord labels plus rent terms and dates. Projected agreement terms and status must match the authorized source tenancy; private payee IDs, account data, documents and raw records are omitted. The browser register consumes this read endpoint only; create/review actions remain unavailable until connected to command services.

`createMyLandlordPortfolioListUseCase` provides the proposed `GET /api/estate/estates/:estateId/landlord/portfolio` read seam. Resolve the authenticated actor's estate access, then query currently effective active ownership links with verified evidence and only same-estate/property tenancy data before projection. Each property is returned once through a strict allowlist; property status and tenancy party/status/date/rent terms must match their linked records and exact decimal/currency precision. The projection excludes private agreements, owner evidence, account/payment destinations, invoice allocation internals and unrelated tenant data. Bind the resolver and repository to existing Zvend identity, property, tenancy, RBAC and billing services before exposing the route.

`modules/properties/structure.js` validates estate hierarchy nodes (zone, street, building and floor) against trusted estate policy, same-estate active parent nodes and optional code/building metadata. Parent shapes and required codes stay configurable because the product contract does not mandate one hierarchy for every estate. It plans non-destructive node archival only after a complete child/property relationship check.

`modules/properties/manage-estate-structure.js` provides injected estate-scoped structure create and list use cases. Creation resolves active parent nodes, applies server-owned type/parent rules, checks optional estate-scoped code uniqueness, then commits the node and audit event together. Listing requires structure-view permission and rejects cross-estate or improperly included archived results.

`modules/properties/update-estate-structure-node.js` handles the Phase 2 structure-update command. It locks the node, accepts only name/code/parent/building metadata/order changes, resolves active same-estate parents, revalidates configured hierarchy rules and child compatibility, then commits and audits atomically. Estate, node type, lifecycle state and system metadata cannot be patched through this operation.

`modules/properties/archive-estate-structure-node.js` locks the node, requires a complete check for child nodes and attached properties, and atomically archives and audits the node without deleting its history. Structure archival must serialize with writers that create or reparent child nodes and properties.

`modules/properties/archive-property.js` checks archive permission, locks the property, requires a complete blocker check across active occupancy, tenancy, billing and access relationships, then archives and audits in one transaction. The adapter must preserve all historical property, ownership, occupancy, billing, tenancy and access records. Property locking must serialize archive against workflows that create new relationships.

`modules/properties/ownership.js` prepares effective-dated user or legal-entity ownership interests, validates optional exact-decimal shares, plans evidence verification/rejection, and closes an interest without deleting its history. Multiple-owner coexistence, share capacity, evidence access and effective-date rules are supplied by trusted estate/property services; these planners do not grant landlord permissions or billing access by themselves.

`modules/properties/create-ownership-interest.js` creates an ownership interest under estate permission and a locked property record, resolves the owner through existing identity/legal-entity services, checks configured co-ownership/share capacity, verifies any private evidence reference, and commits the interest plus audit entry together.

`modules/properties/decide-ownership-verification.js` and `modules/properties/end-ownership-interest.js` apply review and end-date decisions to locked, estate-scoped ownership records. Review requires ownership-review permission and verifies evidence through the private file adapter before approval. Ending preserves the record and requires the existing estate date-policy adapter to approve the effective date. Each use case commits the state change and audit entry in one transaction.

`modules/people/resident-membership.js` plans resident join-request creation and decisions, keeping resident membership separate from optional property occupancy. `modules/people/create-resident-join-request.js` composes request creation with estate policy, applicant eligibility, optional same-estate property lookup, duplicate-open-request locking, private evidence ownership checks, persistence and audit in one transaction. It returns no document references. Approval returns membership and optional occupancy effects for one transaction; rejection requires a reason. `modules/people/tenancy.js` validates tenancy terms using an exact decimal string, configured currency precision, explicit payees and rent frequency, and plans activation, cancellation, termination, a separate linked renewal record, and renewal activation. Renewal creation never edits the prior terms. Renewal activation requires a server-calculated valid handoff window, closes the prior occupancy at the configured instant when needed, and activates the new occupancy in one plan. Date continuity, user/payee verification and concurrency constraints remain adapter responsibilities aligned to Zvend's date conventions. These modules do not manage identity, role grants, ownership verification, notifications or persistence.

`modules/people/decide-resident-join-request.js` adds an estate-scoped use case around the join-request planner. It checks reviewer permission, locks a request inside the selected estate, validates the property there on approval, and commits membership plus optional occupancy effects and audit together. ## Integration gates

- Resolve the current actor and platform permissions through existing Zvend authentication/RBAC.
- Load application records through a repository that scopes access to the applicant or assigned platform reviewer.
- Perform approval's application decision, estate activation, first membership/role assignment, and audit write in one transaction; do not partially apply the returned effects.
- Commit resident join decisions, membership/occupancy changes and audit events atomically; serialize tenancy activation and enforce the one-active-tenancy rule in persistence.
- Use existing IDs, status vocabulary, error envelopes, timestamps, logging, and migration conventions.
- Add adapter-level authorization and transaction tests in the actual source repository before exposing routes.

`estate-dashboard/apply.html` can use the proposed authenticated application API when the host sets `window.ZvendEstateConfig.applicationApiUrl` (the applications collection URL) or `apiBaseUrl` (the API root). It creates a draft with `POST /api/estate/applications`, saves canonical partial fields with `PATCH /:applicationId`, and submits `POST /:applicationId/submit` with `{ documentIds }`. Requests use same-origin credentials; actor identity is never sent in the payload. The HTTP adapters must bind these routes to the existing authentication context and the onboarding use cases above.

The browser does not assume a document upload URL or storage provider. The host may provide `uploadApplicationDocument({ applicationId, file, category, idempotencyKey })` through the existing private-file service; it must return `{ documentId }` only after attaching the uploaded record to that applicant-owned draft. The submission adapter must ignore client claims about verification and load verified categories from trusted file metadata for the locked application. The browser holds uploads in memory for retry and does not persist raw files or document IDs across navigation. `applicationDocumentCategories` may provide the category IDs/labels shown in the form, but the server's submission policy remains authoritative.

## Standalone estate expense workflow

The Nest API now persists estate-scoped expense categories, opaque payee destination references, approval policies, draft requests and decision history. Routes are under `estate/estates/:estateId/expenses` and require an authenticated active estate membership with the finance role for reads and workflow actions; policy, category and payee configuration requires an estate administrator or finance manager. Submissions snapshot the active policy version, approval decisions lock the request row, reject decisions require a reason, and requesters cannot approve their own expenses. A distinct second approver can be required by policy.

The policy can explicitly permit unbudgeted requests; otherwise an eligible approved budget line is required. Payee verification records an authorized offline check of an opaque `ref:` destination identifier. Do not put bank or account numbers in this field. Approval itself does not transfer funds or record payment. The estate manager web UI is available at `/admin/`.

Estate budgets are now persisted under `estate/estates/:estateId/budgets`. Finance administrators create versioned period/category allocations; submission and approval/rejection are audited, and the creator cannot approve their own budget. Approved periods cannot overlap. An exact-period revision can supersede its prior version only before approved expense commitments exist. Expense drafts may reference an approved same-estate budget line. Final expense approval locks that line and checks committed approved requests against the allocation. Budget summaries derive allocated, committed, paid and available values from records. When policy disallows unbudgeted requests, an approved eligible budget line is required.

`POST estate/estates/:estateId/expenses/:expenseId/settlements` records a staff-verified offline bank transfer. It requires an administrator or finance-manager membership, an idempotency key, a transaction reference, received date, positive fixed-precision amount and a verification note. The transaction locks the approved expense, prevents duplicate estate bank references and overpayment, updates `APPROVED` to `PARTIALLY_PAID` or `PAID` from the remaining balance, and writes an audit event atomically. Residents are not given bank reference or verification-note data by this manager-only endpoint. Receipt numbers are references only; no receipt document, bank feed, payment initiation, refund or reversal flow is connected.

## In-app estate notifications

`GET /api/v1/notifications/mine` returns up to 100 notification records for the authenticated user, limited to estates where the user has an active membership. `POST /api/v1/notifications/:notificationId/read` is recipient-scoped and idempotent. Expense review/payment and security incident report/status events insert inbox notices in the same database transaction as the source event. The `(estate, recipient, eventKey)` unique constraint makes event enqueue retries safe. Notices contain bounded display text and a source UUID, not recipient contact data or private incident descriptions. The Flutter resident and manager apps expose the same inbox. Delivery is in-app only; push/email/SMS providers and preference controls are not configured.

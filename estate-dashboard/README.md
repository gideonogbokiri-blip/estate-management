# Zvend Estate dashboard preview

The dashboard uses a restrained estate-operations visual system: warm neutral surfaces, Zvend green accents, compact operational cards and mobile-friendly layouts. The supplied Homely marketplace screens are visual references only; this dashboard does not add property discovery, listings or agent-contact flows.

Open `index.html` directly in a browser. The preview uses plain HTML, CSS and JavaScript and has no build or package-install step.
Open `resident.html` for the mobile-first resident experience.

## Included screens

- Estate operations overview and property register with a schematic estate map/list switch, searchable property records, ownership shares/effective dates, lifecycle history, estate structure across zones/streets/buildings/floors, and occupancy metrics separate from operational maintenance status.
- The property register can load the proposed authorized list seam through `properties-live.js`: configure `propertyListUrl` or `apiBaseUrl`, `currentEstateId`, and the host's authenticated `request` adapter (same-origin `fetch` is supported). It sends bounded search/pagination to `GET /api/estate/properties`, validates the estate and allowlisted row fields, and replaces sample records in connected mode. Set `propertyDetailUrl` to a route template containing `{propertyId}` or `:propertyId` when it differs from `apiBaseUrl`; otherwise detail uses `GET /api/estate/properties/:propertyId`. The modal renders only the authorized property/ownership/occupancy summary and shows unavailable messages for history, documents and charges until their own reads exist. The schematic map remains preview-only, and create controls remain unavailable until connected commands exist.
- The estate structure tab can load `GET /api/estate/structure` through `structure-live.js` using `structureListUrl` or `apiBaseUrl`, the selected estate, and the same authenticated request adapter. It validates a safe node summary, replaces local nodes, and shows loading/empty/error states. Add/edit/archive stay disabled until the corresponding estate-authorized commands are connected.
- Estate structure preview includes local add, rename and archive interactions; it demonstrates configurable hierarchy and blocks archive while children or linked properties remain. It does not save records or enforce connected estate policy, authorization, concurrency or audit behavior.
- Property creation preview collects code, type, operational status, hierarchy, address, description and optional coordinates. New properties appear as vacant until a separate occupancy record exists; this preview does not persist data, enforce estate code uniqueness or place new assets on the schematic map.
- Property details open from both list and map views and include an archive eligibility preview; record history and owner/occupancy samples are illustrative only. The archive action does not run until a connected service verifies that active occupancy, tenancy, billing and access links are clear.
- Property detail includes a separate occupancy list with local add/end actions, effective dates and lifecycle history. Occupancy changes do not grant membership, ownership or billing rights and do not update Zvend access.
- Property details include an ownership-interest form for an existing Zvend user or approved legal entity, optional shares and effective dates, with local preview actions for verification and ending an interest. These actions are illustrative only and do not resolve users/entities, upload or verify documents, enforce estate policy, write audit history or call a Zvend service.
- Resident membership review with local approval preview.
- Estate staff resident register separates pending join requests, all records and active residents; search filters applicant/member name, email and property in the page preview.
- Team & access has local active/invitation filters, search, and a staff invitation preview for existing Zvend accounts with a constrained estate-role list and role-derived scope summary. It does not send invitations or grant permissions.
- Active staff row actions show estate role/scope and preview reason-required suspension or revocation; own access controls are disabled. No membership or audit history is changed.
- Resident join-request review dialog with applicant/property context, private-document boundary, membership/occupancy distinction, reason-required rejection and local status history. Decisions remain in page memory and do not send applicant notifications or write membership, occupancy or audit records.

- Visitor pass overview for resident hosts and gate operations.

- Separate gate operations view with current visitor entry/exit preview and incident follow-up queue.
- Resident safety report form and recent incident preview; submissions remain in page memory and are not sent or stored.
- Estate billing and rent invoice list.
- Finance overview with budget lines, expense requests and local approval preview.
- Maintenance request queue with assignment, allowed status transitions, resolution reasons, resident-visible updates and a separate private staff-note field; changes stay in page memory only.
- Facility directory and resident booking request review.

- Platform application queue includes status/search filters and page controls. Without host-provided `window.ZvendEstateConfig.apiBaseUrl` or `applicationQueueUrl`, it filters sample rows locally and labels them as preview data. When configured, it requests the proposed platform queue endpoint with same-origin credentials, renders only the queue summary, and shows request errors without falling back to sample records. Expanding a live row requests the actor-authorized application detail endpoint and displays safe applicant/document metadata only; document links use the separate short-lived access route. Start-review, request-information and reject actions call their proposed server commands; estate approval remains separate because it requires selecting an eligible initial administrator.

- Applicant estate registration journey at `apply.html`, covering estate/location, owner/operator, structure, supporting documents and a review summary. With `window.ZvendEstateConfig.applicationApiUrl` (or `apiBaseUrl`) configured, each completed section creates/updates an authenticated draft and final submission uses the host's `uploadApplicationDocument({ applicationId, file, category, idempotencyKey })` adapter before calling the proposed submit route. The uploader must use Zvend's private file service and return `{ documentId }`; the backend must independently verify applicant, application attachment, upload state and category. Load the host config before `application-form.js`, for example `<script>window.ZvendEstateConfig = { applicationApiUrl: '/api/estate/applications', request: existingApiClient, uploadApplicationDocument: existingPrivateFileUploader, currentUser: { displayName, email, phone } };</script>`. `applicationApiUrl` is the collection URL. `apiBaseUrl` is accepted as a convenience and appends `/api/estate/applications`. `request` is optional; use it to reuse Zvend's API client, including its CSRF and response-envelope behavior. It receives `{ url, method, payload, credentials }`, returns a parsed response (or a `Response`), and should throw on API errors. `currentUser` is for field prefill/display only and never establishes identity or permission. Configure `applicationDocumentCategories` only when its IDs match the server's accepted category identifiers.

For the estate selector, the same host config may provide `accessibleEstatesUrl` (otherwise `apiBaseUrl` plus `/api/estate/estates`), `currentEstateId`, and `selectEstateContext({ estateId, estate })`. The list projection is for selection only. The callback must fetch `GET /api/estate/estates/:estateId` to obtain the authorized detail summary, then perform the host application's normal context switch and reload estate-scoped views using that summary. The server must recheck membership for the detail and each module request; a UI-only title change is not sufficient.

For the live estate overview, configure `dashboardSummaryUrl` or `apiBaseUrl` plus `currentEstateId` before `dashboard-summary.js`. The default request is `GET /api/estate/reports/dashboard`; the host must first establish the selected estate through its authenticated context mechanism. The server derives the actor from the authenticated session and rechecks estate membership and section capabilities for every request. The host may provide the shared `request({ url, method, credentials })` API client and should set `currentUser` and `currentEstate` from the authenticated, authorized context for shell display. After `selectEstateContext` switches estates, update those config values and call `window.refreshEstateDashboardSummary()` or dispatch `estate:context-changed`; the dashboard clears old metrics while loading, ignores responses from prior contexts, and rejects a response whose estate ID does not match the selected context. The response must include `estateId`, `asOf`, `period` (`startAt`, exclusive `endAt`, `timeZone`), capability-filtered `sections`, and `sourceFreshness`. Each section reports `available`, `incomplete`, `pending_reconciliation`, or `unavailable`; finance amounts are exact decimal strings with a currency code and scale. Unavailable sources display as unavailable rather than as zero. The reporting contract documents the backend response and adapter requirements.

The preview calls `GET /api/estate/expenses` with estate, status, search and pagination parameters. The response must include actor-authorized `{ items, page, pageSize, total, totalPages }`; payment amounts must derive from verified expense allocations. The budget panel uses `budgetSummaryUrl` or `apiBaseUrl` plus `GET /api/estate/finance/budgets`; it shows the effective approved budget line amounts as committed, paid from verified allocations, and available after commitments. The server resolves the estate-local business date, marks effective periods, and sorts those versions first; the endpoint returns up to 24 versions. Connected mode removes sample expense rows and budget figures; the expense-creation control stays disabled until a connected command is implemented. This adapter does not submit approvals or payments.

For current gate visitors, load `gate-visitors-live.js` after `app.js`. To expose manual admission, configure `currentPermissions` from the authenticated host context with the `visitor.override` capability and `manualAdmissionUrl` (a route template with `{gateId}`) or use `POST /api/estate/security/gates/:gateId/manual-admissions`. To enable exit recording, also configure `gateVisitCheckOutUrl` with a `{visitId}` placeholder for the transactional `POST /api/estate/security/visits/:visitId/check-out` command. The browser confirms exit and removes the visit only after the server confirms it. These adapters remain provisional until bound to Zvend's real authenticated request, rate-limit, database and audit services.

## Intended integration boundary

This preview clarifies interface workflows only. Once the Zvend source repository is available, audit its backend, database, authentication, permissions, payment and storage conventions before replacing the local preview actions with authenticated estate APIs. Apply server-side estate scoping and audit every privileged or financially consequential state transition.

`Zvend_Estate_Visitor_Security_Contract.md` describes the proposed credential lifecycle, gate scope, access-event history, incident workflow and integration checks. It is a design contract, not implemented Zvend security behavior.

`Zvend_Estate_Billing_Payments_Contract.md` describes the proposed charge, rent, invoice, verified payment, receipt and reconciliation workflow. It is a design contract, not a connected checkout or confirmed Zvend payment API.

`Zvend_Estate_Operations_Contract.md` describes the proposed maintenance request, staff update, facility availability and booking workflow. It is a design contract, not a connected request or reservation service.

`Zvend_Estate_Access_Reports_Contract.md` describes proposed estate permission grants, staff lifecycle, settings versioning and scoped reporting/export rules. It is a design contract, not a connected authorization or reporting service.

`Zvend_Estate_Property_Mapping_Contract.md` describes asset coordinate storage, estate boundaries, map-layer permissions and the no-person-tracking rule. It is a design contract, not a live map service.

`Zvend_Estate_Platform_Subscriptions_Contract.md` describes proposed configurable plan versions, estate subscription agreements, entitlement history and separation from resident charges. It is a design contract, not a connected platform billing service.
